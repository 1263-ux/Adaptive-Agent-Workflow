# Outcome, Delivery & Learning

## Acceptance
Define desired outcome, constraints, acceptance approach and evidence needs. Acceptance varies by domain. Result states: ACCEPTED (meets goal and constraints), PARTIAL (useful result with explicit gaps), NOT_ACCEPTED (core goal unmet or unacceptable risk). Status must be supported by artifacts and proportionate evidence.

## Evidence
Evidence may be runtime behavior, tests, screenshots, data, source citations, user paths, review records or build artifacts. Require evidence for important claims, not every micro-action. 'File changed', 'tests passed' and 'end-to-end behavior correct' are different claims.

## Risk gates
Security, privacy, destructive data changes, external sending, production deployment and other high-impact actions follow host permissions and user authorization. Quality scores cannot offset permission violations.

## Failure adaptation
Identify cause before adding input, changing method/Skill, adding specialist help, narrowing scope, probing, adjusting dependencies, rebuilding context, asking the user or stopping. Do not blindly retry the same path.

## Learning and metrics
Retain reusable task type, chosen method, capability reference/version, quality, time/cost, human corrections, failure causes, applicability and next-time advice. Evaluation dimensions: outcome quality, time to first value, end-to-end time, human intervention, resource efficiency, adaptability and capability-selection quality. Test count, rule count, Agent count and workflow completion are diagnostic only.
